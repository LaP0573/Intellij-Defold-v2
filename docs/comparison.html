§The short version

Recommendation: fork Intellij-Defold — don't start from scratch

It's the most IDE-grade of the three and already contains the hardest thing to build: a complete, tested native MobDebug debugger. Neither VSCode extension has a real debugger of its own. It also owns build/run end-to-end and has a working hot-reload foundation. The missing pieces are additive.

The crash that blocks it is tiny

openProjectAsync (a suspend fun the platform runs on a background thread) calls runWithModalProgressBlocking, which is EDT-only → throws on every open. Fix ≈ 10 lines + one test-mock update. Not a sign of rot.

§They share the plumbing — they differ on the bet

All three independently locate the editor install, parse its config for the bundled JDK + editor.jar (which holds Bob and dmengine), and download Lua API annotations. What separates them is the core product decision.

Intellij-Defold

"Be a true IDE"

Own the run loop, build a real debugger, integrate hot reload directly with the engine. Editor-independent and most self-sufficient — but stopped at coding + debugging (no bundling, no scaffolding, no URL autocomplete).

Defold Kit

"Headless completeness"

Do everything through bob.jar so you never need the editor — including the full bundle / sign / deploy matrix for 6 platforms. No debugger or language server of its own (both delegated).

Defold Buddy

"Companion to the editor"

Delegate build / bundle / reload / debug to the running editor over HTTP, and add what a text workflow lacks: URL autocomplete, scaffolding, dependency/asset browsing, live log streaming.

§What IntelliJ is missing — ranked

The port targets, by value for an IDE-grade Defold experience. Tier 1 is where to spend first.

TIER 1

High impact · differentiating

  1. Defold URL autocomplete — the most-wanted missing feature; greenfield in IntelliJ but a clean port (CompletionContributor for Lua + a .go/.collection index service). from Buddy
  2. Cross-platform bundling + mobile/web export + signing — the largest functional gap; mostly new Bob command construction + a platform-picker UI (the editor-config plumbing already exists). from Kit
  3. Harden hot reload — make it work for normal runs and editor-launched games, and verify the engine route (today it's debug-run-only and untested end-to-end).
TIER 2

Strong quality-of-life · moderate effort

  1. Per-dependency Lua annotations (extract lib .lua from .internal/lib zips). from both
  2. Scaffolding: create game object / gui / lua module; generate app-manifest; generate hashes module. from Buddy
  3. Add-dependency-from-GitHub + optional Asset Portal browser. from Buddy
  4. Robust running-game discovery (SSDP/UPnP) + live log streaming for games not launched by the IDE. from Buddy
TIER 3

Nice to have · longer horizon

  1. Teal support — niche but unique. from Buddy
  2. Build-error → Problems panel (a Bob output problem matcher) — none of the three has this; a real differentiator.
  3. Project scaffolding / new-project wizard. from Kit
  4. game.project settings form / validation; native-extension support.

Out of scope (for all three): scene / visual authoring (collection / .go / .gui / atlas / tilemap editors). The realistic posture everyone shares: code + build + debug in the IDE, author scenes in the official Defold editor.

§Where IntelliJ already wins

For balance — the reasons forking beats rewriting:

• A real, native debugger (the others have none of their own).
• Owns the run loop (build → extract matching dmengine → launch → parse logs) with no dependency on a running editor or a third-party debug extension.
• Self-implemented hot reload straight to the engine — no editor required (needs hardening, not a rewrite).
• IDE niceties: clickable file:line console links, log-severity coloring, file icons, templates, and disabling of conflicting IDE build actions.
